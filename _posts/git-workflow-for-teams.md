팀으로 개발할 때 브랜치 전략은 협업 효율과 배포 안정성을 좌우합니다. 주요 워크플로우를 비교하고 팀 상황에 맞는 선택을 할 수 있도록 정리합니다.

## Git Flow

Vincent Driessen이 제안한 전통적인 브랜치 전략입니다.

```
main        ──●──────────────────────────●──
              │                          │
develop     ──●────●────●────●───────────●──
                   │    │    │
feature           ●──●  │  ●──●
                        │
release              ●──●
                        │
hotfix              ●───●
```

**브랜치 역할:**
- `main`: 프로덕션 배포 코드
- `develop`: 다음 릴리즈를 위한 통합 브랜치
- `feature/*`: 기능 개발
- `release/*`: 릴리즈 준비 (버그 수정, 문서화)
- `hotfix/*`: 프로덕션 긴급 수정

**적합한 팀**: 명확한 릴리즈 주기가 있는 팀, 여러 버전을 동시에 지원해야 하는 제품

## GitHub Flow

GitHub이 사용하는 단순화된 워크플로우입니다.

```
main     ──●──────────────────────●──
            │                    │
feature    ●──●──●──● (PR) ──●──●
```

**규칙:**
1. `main`은 항상 배포 가능한 상태 유지
2. 작업은 `main`에서 브랜치 생성
3. 자주 푸시하여 팀과 공유
4. PR을 통해 리뷰 후 머지
5. 머지 후 즉시 배포

**적합한 팀**: 지속적 배포(CD)를 실천하는 팀, 소규모~중규모 팀

## Trunk-based Development

모든 개발자가 `main` (trunk) 에 직접 또는 단기 브랜치를 통해 자주 커밋합니다.

```
main  ──●──●──●──●──●──●──●──●──
         └─┘  └──┘      └──┘
        단기 브랜치 (1-2일)
```

**핵심 실천사항:**
- 하루에 한 번 이상 main에 통합
- Feature Flag로 미완성 기능 숨기기
- 강력한 CI/CD 파이프라인 필수

**적합한 팀**: 대규모 팀, 빠른 이터레이션이 필요한 스타트업

## 커밋 메시지 컨벤션

어떤 워크플로우를 선택하든 일관된 커밋 메시지는 필수입니다.

```
feat: 로그인 기능 추가
fix: 모바일에서 레이아웃 깨지는 버그 수정
docs: API 문서 업데이트
style: 코드 포매팅 (기능 변경 없음)
refactor: 인증 모듈 리팩토링
test: 결제 서비스 단위 테스트 추가
chore: 의존성 업데이트
```

## PR 리뷰 체크리스트

```markdown
## 리뷰 체크리스트

- [ ] 코드가 요구사항을 충족하는가?
- [ ] 테스트가 작성되었는가?
- [ ] 엣지 케이스를 처리하는가?
- [ ] 보안 취약점은 없는가?
- [ ] 성능에 영향을 주는 변경은 없는가?
- [ ] 문서/주석이 업데이트되었는가?
```

## 마치며

정답인 워크플로우는 없습니다. 팀의 크기, 배포 주기, 제품의 특성에 따라 가장 적합한 전략을 선택하고, 팀 전체가 규칙을 이해하고 따르는 것이 중요합니다.
